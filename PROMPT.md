# Prompt for Claude Opus 5.5: build "PizzaDrop" — a FilePizza-style P2P file sharer

> Copy everything below the line into Claude Opus 5.5. If you have a screenshot of the
> reference background effect, attach it alongside this prompt where marked.

---

Build me a complete, production-quality web app similar to **FilePizza**: a browser-to-browser
(peer-to-peer) file transfer tool where the sender drops a file, gets a short link and a QR code,
and keeps their tab open until the receiver has finished downloading. The file never touches
a server's disk; it streams directly between browsers over WebRTC.

## Core requirements

### 1. Sending a file
- The landing page is a single, full-screen drop zone. Dropping a file (or clicking to pick one)
  immediately starts hosting it. No sign-up, no settings, no confirm step.
- **No file size limits.** Do not read the whole file into memory. Stream it in chunks
  (e.g. 64 KB–256 KB) from a `File`/`Blob` via `slice()` and back-pressure on the WebRTC
  `RTCDataChannel` (`bufferedAmount` / `bufferedamountlow`) so multi-GB files work without
  crashing the tab.
- Support multiple files dropped at once (send them sequentially, or zip on the fly client-side
  if that is simpler; either is fine, but state which you chose).
- After a drop, show:
  - the **short link** (see §3),
  - a **QR code** of that link (see §4),
  - a **"keep this tab open"** notice,
  - live transfer status: number of connected receivers, per-receiver progress bar, speed, ETA.
- Warn with `beforeunload` if the sender tries to close/refresh the tab while a transfer is in
  progress or while the file is still being hosted.

### 2. Receiving a file
- Opening the link shows the file name, size, and a single **Download** button.
- On click, the receiver connects to the sender over WebRTC and streams the file straight to disk:
  - Prefer the **File System Access API** (`showSaveFilePicker`) when available so bytes go to
    disk as they arrive (needed for very large files).
  - Fall back to a **Service Worker–backed streaming download** (StreamSaver-style
    `ReadableStream` piped into a `Response` served by the SW) so Firefox/Safari still get true
    streaming downloads without buffering the whole file in RAM.
  - Last-resort fallback: buffer into a Blob and trigger a download (only for small files; show
    a warning above e.g. 500 MB).
- Show progress, speed, ETA, and a clear "Done ✓" state. Verify integrity with a rolling hash
  (e.g. incremental SHA-256 via WebCrypto or a small WASM/JS hasher) and show a mismatch error
  if the hash differs from what the sender announced.
- Multiple receivers can download the same file at the same time from the same sender.

### 3. Short links
- Links must be **short**: `https://<domain>/<code>` where `<code>` is 5–6 characters from an
  unambiguous alphabet (no `0/O`, `1/l/I`). Example: `https://pzza.app/x7k4q`.
- The code is generated by the signaling server and maps to the sender's session. It expires
  when the sender's tab closes (or after a configurable idle TTL, default 24h).
- Provide a one-click **Copy link** button with visible "Copied!" feedback, and use the
  Web Share API (`navigator.share`) on mobile when available.

### 4. QR code
- Render a QR code of the short link on the sender page, large enough to scan from a phone
  across a desk (at least ~220 px, high error-correction level M or Q).
- Scanning it with **any** camera / QR app must open the plain `https://` link in the browser,
  which lands directly on the receive page and starts the flow. No custom URL scheme, no
  app-intent wrapper — just the URL.
- Generate it client-side (e.g. the `qrcode` npm package, or a tiny inline QR encoder) so no
  third-party service sees the link. Style it to match the theme (light modules on black is
  fine as long as it still scans reliably; test it).

### 5. Networking
- WebRTC `RTCPeerConnection` + `RTCDataChannel` (ordered, reliable) for the file bytes.
- A small **signaling server** (Node.js + `ws`, or a Cloudflare Worker + Durable Object — pick
  one and justify it) that:
  - issues the short code,
  - relays SDP offers/answers and ICE candidates between sender and receivers,
  - tells the sender when a receiver connects/disconnects,
  - never sees file contents.
- Include public STUN servers and make TURN configurable via env vars (explain how to add
  a TURN server such as coturn for NAT-restricted peers).
- Handle reconnects gracefully: if a receiver drops mid-transfer, the sender should not crash
  and other receivers should be unaffected.

### 6. Tech stack
- TypeScript throughout. A modern bundler/framework (Vite + React, or SvelteKit, or Next.js —
  pick one and justify it briefly). Keep dependencies minimal.
- Repo layout: `client/` (or `app/`), `server/`, shared types in `shared/`.
- `README.md` with: what it is, how it works (diagram in text is fine), local dev steps,
  deployment steps (Docker or a one-click host), env vars, browser support matrix, known limits.
- Lint + typecheck pass. Add a few unit tests for the chunking/back-pressure logic and the
  short-code generator.

## Visual design (this matters — follow it exactly)

The whole app is dark-mode only, **pure black background (`#000000`)**, with an animated
**color ASCII-art illustration of a pizza slice** as the hero/background element.

### The pizza slice
- It is an *illustrative* pizza slice (cartoon/vector style — crust, cheese, pepperoni, maybe
  a basil leaf), **not** a photo.
- Render it in **animated colour ASCII style**: the slice is drawn entirely from monospace
  text characters (`@ # % * + = - : . ` etc., densest characters for the darkest/most saturated
  areas), each character coloured from the underlying illustration (warm reds/oranges for
  pepperoni and sauce, yellows for cheese, tan/brown for crust, green for basil). It should
  animate: a gentle shimmer / colour-drift / flicker across the characters — think an ASCII
  render that slowly "breathes" — looping smoothly, subtle enough not to be distracting.
  *[If a reference screenshot is attached, match its look as closely as possible.]*
- Implement it as a `<canvas>` (or a pre-rendered character grid) driven by
  `requestAnimationFrame`. Do this by shipping a small illustration (inline SVG or PNG you
  generate), sampling it to a character grid at runtime, and animating the colours. Keep it
  at 60 fps on a laptop and pause the animation when the tab is hidden.
- **Orientation:** take the slice with its pointed tip (the cone / apex) pointing **straight up**,
  then **rotate it 45° clockwise** (tilted to the right). The crust ends up at the lower-left,
  the tip at the upper-right.
- **Position:** centred in the viewport, both horizontally and vertically, occupying roughly
  45–60% of the smaller viewport dimension. It must stay centred and scale correctly on
  resize and on mobile.
- Everything else on the page is **pure black**. No gradients, no vignette, no grid, no noise
  texture.

### The scattered "stars"
- On top of the black, place a **maximum of 15** single random ASCII characters (`.`, `*`, `+`,
  `'`, `:`) very far apart, like sparse stars. Random positions (never overlapping the slice),
  very dim (e.g. 20–35% opacity white/grey), and optionally each one twinkles on its own slow
  random cycle. They are re-seeded on page load, but the count never exceeds 15.

### UI on top of the art
- The drop zone, link, QR code, buttons and progress UI float over the artwork in a minimal
  monospace-friendly style (a monospace font for headings/links fits the ASCII theme; a clean
  sans-serif is fine for body copy). Small, tasteful, high-contrast; never obscure the slice
  more than necessary — e.g. a compact panel at the top or bottom, or a translucent black card
  that only appears after a drop.
- Provide a `prefers-reduced-motion` fallback that renders the slice static.
